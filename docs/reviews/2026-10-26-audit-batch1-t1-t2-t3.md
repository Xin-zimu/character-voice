## 一、T1 · AUD-11 的变异锚点

### 复现

`M50`（把「单句 ≤ 15 字」的旧硬约束写回种子文件正文）当时**是绿的**：
跑 `py scripts/mutation_check.py --only M50` 得到「✓ 已拦住」，
`test_37_seed_notes_are_not_runtime_rules` 报红，一切看起来都对。

问题在于**它把规则写回了哪里**。原实现用一个固定锚点：

```python
text.replace('\n---\n\n## 这份文件不再用于什么（AUD-11）',
             dead + '\n---\n\n## 这份文件不再用于什么（AUD-11）', 1)
```

实测差异（`difflib` 比对，修复前）：

```
@@ -69,4 +69,7 @@
 > 保留下来的只有两条，且已改写进角色卡，不靠这句话生效：……
 
+
+**可执行的硬约束**：日常对话单句 ≤ 15 字；……
+
 ---
```

也就是说，那句「可执行的硬约束」被插在**「这条硬约束已作废」那一段说明之后**。

它仍然会让 `test_37` 报红，所以「已被拦住」这句话本身没撒谎；但这个变异
模拟的**不是** AUD-11 当初的处境。当初那条规则是写在统计表下面、以可执行
的口吻直接下达的；插在作废说明之后，读者先看到的是一段解释它为什么不算，
再看到的才是一句孤立的规则——两者对读者的影响不同，对判据的触发点也不同。

**结论**：证据链断在「变异改到了目标文件」这一步——文件确实被改了，但改到
的不是它声称要改的那个位置。

### 另一半：作废标记本身没有任何变异覆盖

`test_37` 有三条判据（① 必须有「不是运行规则」声明；② 不许有未标作废的
限制性句子；③ 判据不能靠空集通关）。M50 碰的是第 ② 条的前半。
**把作废标记拿掉**——去掉 `~~删除线~~`、把「已作废」改成中性词——这一整类
从来没有变异覆盖过。而它才是 AUD-11 落在文件上的实际形式。

### 修复

1. 锚点改成**它原来的位置**：统计表最后一行之后、作废说明之前。
   并在函数里直接断言：插入点必须在这一节内，**且排在「那条被划掉的旧硬约束」之前**。
   第一版改成「插在本节末尾」，实测立刻报 `变异失效：写回的位置不在原来那一节里`
   —— 因为本节末尾已经越过了下一个 `## `。这条断言是它自己抓出来的。
2. 新增 **M84**：抹掉删除线与「作废」字样，让规则重新生效。它锁的是 M50 没覆盖的那一半。
3. `run_mutations()` 每次变异前增加一条校验：**磁盘上的文件必须与备份逐字节一致**。
   原实现只在循环开始读一次备份，若某个变异没还原干净，下一条就是在别人留下的
   内容上改——变异和证据会一起错位，而且不会有任何提示。

### 证据

| 步骤 | 结果 |
|---|---|
| 修前跑 M50 | ✓ 已拦住（**但插入点在作废说明之后**） |
| 换锚后第一版 | ! 变异失效：写回的位置不在原来那一节里 |
| 换锚后定版 | ✓ 已拦住，`test_37` 报红 |
| M84（新） | ✓ 已拦住，`test_37` 报红 |

## 二、T2 · 跨平台并发：Linux 的 `fcntl` 掩盖了 Windows 那一层

### 复现

`test_16b_memory_concurrent_writes_do_not_lose_records` 是绿的，M55 也能拦住它。
但这两件事压的都是**第 1 层**锁——`_lock_for()` 那个按绝对路径共享的
`threading.Lock`。第 2 层（跨进程文件锁）**一条用例都没有**：

```
grep -n "msvcrt|fcntl" scripts/test_backend.py → 只在注释里出现（第 1267 行）
```

后果：Linux 上 `fcntl` 一直存在，所以 Windows 分支写错时，**任何平台上的
回归都不会红**。

### 实测（本机 Windows / CPython 3.13.2，6 进程同时写）

| 条件 | 轮数 | 结果 |
|---|---|---|
| 保留两层文件锁 | 8 | 8/8 轮 6 条（另跑 30 轮 + 40 轮，0 异常） |
| 两层文件锁都关掉 | 8 | 8/8 轮丢记录，文件里只剩 **2～4 条** |

第一次跑「关锁」那一组时 worker 有 10 次非零退出，是 `msvcrt` 在空文件上
锁不到字节所致——那是**另一个**问题（见下 M89），修法就是先写 1 个字节。

### 修复

| 用例 | 锁住什么 |
|---|---|
| `test_16d` | **真的起 6 个子进程**，不模拟锁：谁在跑就用真实平台的锁。判据只看结果——都报成功，文件里就必须有 6 条 |
| `test_16e` | 模拟 `msvcrt` 分支：锁文件 ≥ 1 字节、从 0 字节处锁 1 字节、用 `LK_LOCK`；**业务函数抛异常时也必须解锁**（否则下一次写入卡到 `LK_LOCK` 的 10 秒超时，把死锁换成偶发报错） |
| `test_16f` | 锁路径跟着**记忆文件**走；两个世界不共用同一把 |

新增变异：**M87**（两层文件锁都关掉）、**M88**（Windows 锁了不解锁）、
**M89**（不写锁文件种子字节）。

> **M87 第一版是「未拦住」**，而且不是测试的漏洞：只把 `if fcntl is not None:`
> 改成 `if False:`，而下面那条是 `elif msvcrt is not None:`——Windows 上它照样执行，
> 变异根本没生效。这和项目里反复出现的那类误读是同一个（「变异没生效」被读成
> 「测试没拦住」）。现在函数里显式断言两个分支都不再进入。

### 没有做的

**没有在第二台真机上跑过**。本条只在本机 Windows 上执行了真实并发写入；
模拟分支覆盖的是「调用形状对不对」，不是「另一个平台能不能跑」。
`test_16d` 在 Linux 上会走 `fcntl` 分支，但本机没有 Linux 环境可以实测，
这一点不写成「跨平台已验证」。

## 三、T3 · 记忆渲染的静默归零

### 复现（修前实测）

三条 active 记忆，中间夹一条超长记录：

```python
recs = [「你喜欢在活动室看书」, 「一起看过一次黄昏」*200 字, 「怕黑」(summary)]
pb.render_shared_memory(recs, "normal")
```

输出：

```
[1] 2026-10-20 · 对方：你喜欢在活动室看书
```

第二条超预算 → `break` → 第三条（「怕黑」）**根本没被看过**。
用户侧看到的是「明明存了记忆，她一条都不提」，而且**没有任何警告**。

这不是「模型没用好记忆」，是渲染层在进入上下文之前就把它们丢了。
「检索到了」「放进上下文了」「模型用上了」是三个不同的事实，
这条缺陷卡在中间那个。

### 修复

- 每条封顶 `MEMORY_ENTRY_MAX = 300` 字符。**只用「剩余预算」压缩是不够的**：
  一条 5000 字的记录会正好用掉全部预算，后面的照样进不来——从「被整条
  吞掉」变成「被一条压过的长记录吞掉」，用户看到的结果一样。第一版就是这么写的，
  实测输出 1200 字符里 1100 是那条记录。
- 压缩只**截尾**，不概括、不改写，并加「……（后略）」标记。概括会引入
  「记录里没有的话」，那是 CHAT-019 管的事。
- 压不下就跳过这一条，**继续看后面**。
- 编号按**实际装入**的顺序排，跳过的记录不在编号上留空洞。
- 新增 `render_shared_memory_with_meta()`，返回
  `{listed, skipped, truncated, chars, budget}`；`/api/preview` 回传
  `memory_render`，`◇` 面板把三个数分开显示。

修后同一个输入：

```
[1] 2026-10-20 · 对方：你喜欢在活动室看书
[2] 2026-10-21 · 你们一起：一起看过一次黄昏，很长的记录……（后略）
[3] 2026-10-22 · 你：怕黑（由对话摘要而来，可能不准确，不要当成她亲口说过）
META {'listed': 3, 'skipped': 0, 'truncated': 1, 'chars': 399, 'budget': 1200}
```

### 先红后绿

新用例写好之后，先让它们在**修复前的实现**上跑：

```
$ py <旧实现 + 新用例>
Ran 2 tests → FAILED (errors=2)
```

（两条都红，原因是旧实现没有 `render_shared_memory_with_meta`；
这正是「放进上下文了几条」当时无处可查的表现。）

### 为什么没顺手改 `render_hits()`

原作片段那边也有 `if used + len(block) > max_chars: break`。**保留现状**：
每条原作片段是一段完整上下文窗口，从中间截断会把半句话当成完整依据，
比整条不注入更糟。记忆不同——记忆是用户自己写的一句话，截尾仍然成立。
这个不对称是有意的，不是漏改。

## 四、顺手修掉的一条无关真 bug

后端连跑 6 轮，1 轮在 `retriever.py::tokenize` 解释器级崩溃：

```
Fatal Python error: _PyEval_EvalFrameDefault: Executing a cache.
  File "...\retriever.py", line 35 in tokenize
  File "...\server.py", line 165 in load_corpus
  File "...\scripts\test_backend.py", line 198 in _need_corpus
```

`server.load_corpus()` 的锁保证「只存一份」，**保证不了「只建一次」**：
测试主线程建 13070 条索引时，`setUpClass` 起的服务线程可能同时从
`CORPUS is None` 出发。现在 `_need_corpus()` 自己串行化。

修前：6 轮 1 次崩溃。修后：8 轮 + 16 轮，**0 次**。
